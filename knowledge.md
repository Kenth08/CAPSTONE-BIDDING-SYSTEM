# Project Knowledge Base

Domain knowledge for the E-Procurement Blockchain System. This file explains
*what the system means*; [AGENTS.md](AGENTS.md) explains *how to work on it*.

## Purpose

Digitizes a Philippine-style public procurement process (RA 9184 terminology:
ABC, BAC Resolution, Notice of Award, Notice to Proceed, PhilGEPS) and records
every lifecycle step as a hash on the Ethereum Sepolia testnet, so the history
is tamper-evident and publicly verifiable.

## Roles

| Role | What they do |
|------|--------------|
| **Admin** (BAC / procurement office) | Creates projects, reviews supplier registrations, publishes approved projects, evaluates bids, selects winners, issues post-award documents, views reports |
| **Head** (department head) | Approves submitted projects or requests document revisions. Can't reject: the project was approved before it was filed, so the Head's review can correct it but not cancel it (`/reject/` answers 403) |
| **Procurement Staff** (`staff`, BAC Secretariat) | With `BAC_WORKFLOW_ENABLED`: creates, submits and publishes projects, drafts BAC Resolutions and opens voting, issues the BAC Resolution, NOA and NTP. Never votes. Shares the Admin's procurement screens at `/staff` |
| **BAC Committee** (`bac`) | With `BAC_WORKFLOW_ENABLED`: five seats (`BACMembership`: one Chairperson, one Vice-Chairperson, three Members), recorded by the Admin from the Head's office order. Every member evaluates every bid; the Chairperson records post-qualification; members vote on the resolution with a required comment |
| **Supplier** | Registers with compliance documents, bids on projects matching their business category, resubmits flagged documents |
| **Public** | No login: views open biddings, awarded contracts, and verifies the blockchain trail at `/public` |

Demo accounts from `python manage.py seed`: `admin`, `head`, `supplier` (passwords printed by the seed command).

## Procurement lifecycle

```
Admin creates project ──► Head review ──► Admin publishes ──► Suppliers bid ──► Admin evaluates ──► Award ──────────► Post-award docs
   SUBMITTED            HEAD_APPROVED      BIDDING_OPEN        (not anchored)    (not anchored)      EVALUATION_COMPLETED  RESOLUTION_ISSUED
                        HEAD_REJECTED                                                                BID_SUBMITTED*        NOA_ISSUED
                        REVISION_REQUESTED                                                           AWARDED               NTP_ISSUED
```

Each label under an arrow is a `BlockchainAnchor.Stage` written on-chain.
Bid submission and qualify/disqualify are database records (audit-logged). At
award time three anchors are written, in order: `EVALUATION_COMPLETED` (one
salted commitment to every bid + final outcome — no amounts on-chain; salts on
`Bid.commitment_salt`), `BID_SUBMITTED`\* (**winning bid only**) and `AWARDED`.
After award, qualify/disqualify are refused (the evaluation is final).
`BID_QUALIFIED` / `BID_DISQUALIFIED` exist in the vocabulary but are not written.
A tx hash is only "verified on-chain" once `confirm_anchor` has checked the RPC
is Sepolia, read the receipt, found the matching unclaimed `AnchorRecorded` event
and seen `getAnchor(id)` agree (`BlockchainAnchor.chain_status`). It then saves the
on-chain identity (`chain_anchor_id` = contract index, log index, chain time,
chain id, contract) and depth/finality (`chain_finalized` only if the node's
`finalized` block covers it).

### Project statuses (`Project.Status`)

`draft` → `pending_head` → (`needs_revision` ↔ `pending_head`) → `approved` → `published` → `closed` (deadline passed) / `awarded`

- `rejected` and the `HEAD_REJECTED` stage exist only on older projects. The Head can no longer reject, but both stay, because statuses are history and stages are written on-chain.
- `deadline` is **computed at publish time** (today + `bidding_period_days`), never typed in by the Admin.
- `expected_delivery_date` is **computed at award time** (award date + `delivery_period_days`).
- Expired published projects are flipped to `closed` lazily on read (`close_expired_published_projects`) — there is no background worker.
- Project codes look like `PC-7K4M-Q9XT-3HWD` (12 random characters, generated by the backend with `secrets`). Older projects keep `P-2026-001` or `PRC-2026-7K4M-Q9XT` forever: the code is the on-chain index for the whole procurement (project, bids and award) and is never rewritten.

### Supplier eligibility

A published project is only visible to verified suppliers whose business
category matches the project's `category` (see `frontend/src/constants/categories.js`
and `eligible_types`). One bid per supplier per project (DB constraint).
The **Others** category is the exception: it needs a "please specify" description
(`Project.category_other`) and is open to every verified supplier, since no
registered category can match it.

Bid delivery timeline and warranty period are chosen from the lists each project
offers (`Project.delivery_options` in calendar days, `warranty_options` in months;
`procurement/bid_terms.py`). Older projects with no lists keep free text. The bid
keeps the readable label in `delivery_timeline` (part of the anchored bid payload)
and the number in `delivery_days` / `warranty_months`.

Categories are the built-in `PROCUREMENT_CATEGORIES` plus any the Admin adds from the
Planning form (`ProcurementCategory`, `GET/POST /api/categories/`). A project's category
must be one of these, never free text, because nobody could match it. A new category
has no suppliers until they add it (registration, or a category request in Settings)
and has only the base documents.

### Required project documents

Purchase Request, Technical Specifications, Terms of Reference, Approved Budget
document, Bid Evaluation Criteria. The Head can flag individual documents for
revision without rejecting the project.

## Separation of duties (`BAC_WORKFLOW_ENABLED`)

Off (the default): the original workflow above, the Admin prepares, evaluates and awards.
On: Staff prepare and publish; the Admin manages accounts and BAC designations and
oversees read-only; the BAC Committee evaluates (a bid qualifies or is disqualified by
3 of 5 members), the system ranks qualified bids lowest first, the Chairperson
post-qualifies the top candidate (a failure moves the next one up), Staff draft the
resolution for the Lowest Calculated Responsive Bid, members vote with a comment, and
3 approvals adopt it. Adoption generates the resolution PDF (ranking, post-qualification,
every vote and comment) and stores its SHA-256; it is never regenerated. The Head then
approves the award, which runs the original award code and writes the same anchors
(`EVALUATION_COMPLETED`, `BID_SUBMITTED`, `AWARDED`), or returns it with remarks.
Staff issue the BAC Resolution from that frozen file, so `RESOLUTION_ISSUED` fingerprints
exactly what was adopted. No stage, payload or contract changed. Names, votes and
comments stay in the database. Votes are write-once, and seats are ended, never deleted.
For an in-person meeting, Staff may record a member's vote from the ballot or minutes
(`record-vote`): it keeps the member's name, is marked as recorded by Staff, and the member
is notified. A mistake is never edited: the voter or Staff adds a write-once correction note
(`BACVoteNote`), and the vote and count stay as they were. While evaluating (deadline until
voting opens), a seated member can ask a bidder to fix documents; a resolution can't
recommend a bid with flagged documents.
Rules: `procurement/bac.py`; endpoints `/api/bac/...` in `bac_views.py`.

## Blockchain anchoring model

- **Database = source of truth. Chain = independent witness.**
- For each transition the backend builds a canonical JSON payload (only fields that are final at that stage), hashes it together with the stage's evidence document (SHA-256), and stores a `BlockchainAnchor` row.
- The frontend (MetaMask) or the backend (`BLOCKCHAIN_SERVER_SIGNING=True`, web3.py) writes `(entityType, procurementCode, stage, dataHash)` to `ProcurementLedger`, then posts the tx hash back to `/{projects|bids|awards}/{id}/anchor/`.
- A missing tx hash just means "not yet anchored" — retryable, never a failure of the business action.
- Evidence document per stage: see `STAGE_DOCUMENT_FIELD` in `backend/procurement/blockchain.py`.
- `PAYLOAD_VERSION = 2`: v1 included mutable fields (status, deadline, …) which made honest records verify as altered; v1 anchors are still verified through a legacy path.
- Public verification replays the trail from the contract and lets anyone hash a document locally in the browser to compare.

### Payload v3 and commitment openings (built, not active)

`PAYLOAD_V3_ENABLED` is off and the app refuses to start with it on, and every new
anchor is still v2. Only verification is live: `verify_anchor` reads a v3 payload
if one exists (`payload_v3_reader`, in `blockchain.READ_ONLY_RULES`, outside the
registry a writer version must be in). None exists outside tests.

- A commitment is `SHA-256(canonical({kind, private fields, salt}))`, with a fresh
  256-bit salt per commitment. Its "opening" is that exact object, kept encrypted
  and write-once in `CommitmentOpening` for as long as its anchor exists.
- Openings use `COMMITMENT_KEY`, never `FILE_ENCRYPTION_KEY`, and never fall back to
  plaintext. Custody and rotation are in [SECURITY.md](SECURITY.md#6-environment-variables-names-only).
- Bid leaves are sorted by value (Decision F). Existing v2 salts are untouched (Decision C is open).

**Decision A is provisional.** The contract amount is public as the working policy,
subject to applicable procurement disclosure requirements. `payload_v3.AWARD_PRIVATE_FIELDS`
follows it, and stays provisional until the field-by-field policy in
[SECURITY.md](SECURITY.md) ("Award disclosure policy") is reflected in the payload builder,
the public API and the verifier. No v3 anchor may be written before that. If the amount
becomes private, `amount` joins the list and the Notice of Award file stops being public.
`PUBLIC_AWARD_FIELDS` does not exist yet (Phase 6).

**Award time.** `Project.awarded_at` is the exact award instant. It has one writer,
`select_winner`, in the award transaction under the project row lock, and a re-award
is refused. It is stored and hashed in UTC, and the public procurement detail shows only
its Philippine date. `Award.awarded_at` is only a date, taken
from the server process's local clock (Asia/Manila: on the Linux hosts Django sets the process TZ from `TIME_ZONE`). So from 16:00 to 23:59
UTC, a committed `awarded_at` shows the day before the Manila award date: convert to
Asia/Manila before comparing dates. Awards made before this field existed may have no
exact time, and their openings are refused rather than filled in.

### Verification outcomes

Every check ends in one of five outcomes, the same in the server's account
(`verification.summarize`) and the browser's independent check (`packetVerify.js`):

| Outcome | Shown as | Meaning |
|---|---|---|
| `verified` | Verified | Every check that ran agreed and the transaction was read back. A hash alone never counts |
| `hash_mismatch` | Mismatch | A recomputed hash disagrees: an edited payload or record, or different document bytes |
| `not_found` | Missing evidence | Evidence that should exist doesn't: no transaction, payload, record, kept version or stored file. In the browser: no such ledger record |
| `unconfirmed` | Unavailable or incomplete evidence | Evidence exists but can't be read or decided: storage down, unreadable file, unsupported version, unconfirmed transaction, lost key, incomplete manifest |
| `invalid_tx` | Invalid transaction | A reported transaction failed, was never mined, is malformed, or doesn't record this entry |

Evidence completeness is separate from integrity. Green means one thing, labelled
`SELECTED DOCUMENT VERIFIED — RECORD CHECKS COMPLETE`: in the browser's own check, a v3
record with all five documents recorded, a selected file whose bytes match the version
that record bound, and a transaction read back and agreeing. It is about that one file.
With no file the status is blue, `RECORD MATCH — DOCUMENT NOT CHECKED`, with outcome
`verified` and `green: false`. For a v3 record a skipped transaction check (a pruned
receipt, or no transaction reported) is `unconfirmed`, in blue; v1 and v2 stay `verified`
under their original rules. A transaction hash, a server confirmation or a successful API
response is never green. An incomplete manifest is `unconfirmed`, in amber, labelled
`MATCH — INCOMPLETE EVIDENCE` with the count and names, even with a matching file. v1
and v2 records show a blue legacy status. Results are tied to the record and file they
were computed from, so changing or clearing the file removes them at once.

`document_evidence` checks the exact version an anchor fingerprinted, not the file on
record now. For v1/v2 it stands beside `integrity.document`, which keeps its
original meaning: does the file on record NOW still match? A normal revision makes
that `mismatch` too, so `verification.historical` reports the version evidence beside
the frozen result, and only `tamper_indicated` when it supports that conclusion. A
current file in no recorded version stays `unconfirmed` until Phase 5 sets the rules.

## Glossary

- **ABC** — Approved Budget for the Contract (`Project.budget`)
- **BAC** — Bids and Awards Committee
- **BAC Resolution** — document recommending the award
- **NOA** — Notice of Award; **NTP** — Notice to Proceed
- **PhilGEPS** — Philippine Government Electronic Procurement System (supplier registration certificate)
- **Anchor** — one hashed lifecycle event recorded (or waiting to be recorded) on-chain
